## 二、总策略

**用一个商城后端，把忘掉的知识重新长出来。**

三条主线：能写接口 / 能讲原理 / 能被追问项目。
八股不单独背，全部挂在当天写的代码上——你今天写了缓存，今天就把缓存三兄弟讲掉。

每天固定四块（4 小时，块间休息 5–15 分钟）：

| 时长 | 模块 | 做什么 |
|---|---|---|
| 90 min | 项目实战 | 我讲设计边界和思路 → 你写 → 我 review 并指出问题 |
| 60 min | 原理深挖 | 只讲你今天写的那段代码背后的原理，不扩散 |
| 45 min | 手写 / 追问 | 手写代码，或我连续追问，你口述 |
| 45 min | 复盘 | 口述今天接口的设计取舍，记录 3 个卡点 |

**规则**：卡住 10 分钟就问我。我不给完整答案，给方向、伪代码、报错定位。
状态差的日子只做前两块，不算失败——坐在电脑前焦虑四小时才是失败。

## 六、目录结构（一开始定好，后面不改）

```
mall-api/
├── cmd/server/main.go        程序入口
├── internal/
│   ├── config/               配置加载
│   ├── router/               路由注册
│   ├── handler/              HTTP 层：参数校验、组装响应
│   ├── service/              业务逻辑
│   ├── repository/           数据访问（MySQL / Redis）
│   ├── model/                表结构 & DTO
│   ├── middleware/           鉴权、日志、recover
│   └── pkg/                  通用件：response、jwt、errcode
├── deploy/docker-compose.yml
├── configs/config.yaml
└── README.md
```

**为什么要分三层**（面试必问）：handler 不写业务、service 不碰 SQL、repository 不管 HTTP。
分层不是为了好看，是为了改一个东西时不用翻三个文件。
